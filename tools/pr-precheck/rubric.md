# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-fidelity | Plan context's promised behavior, included/excluded scope, files, and deviation notes compared line by line with the Candidate PR unified diff and commits. | Every behavior-changing hunk implements the issue's bounded plan or a specifically recorded and justified deviation. Directly necessary tests or docs are allowed. A planned part omitted with an honest, explicit deferral in both the plan/deviations and PR description may pass as the narrower stated outcome; a quiet omission, unrelated cleanup, or new feature fails. | required |
| claim-accuracy | Candidate PR title and description, including completion and limitation claims, compared with the diff and the plan's deviations. | The description accurately tells a reviewer what the diff does, what it leaves out, and any meaningful limit. A claim that work is present, complete, or unchanged when the diff contradicts it fails. Brevity and section naming alone do not decide this check. | required |
| decisive-test-evidence | Candidate PR test-evidence section and added tests compared with the Plan context's reproduction trigger, expected-after outcome, controls, and test plan. | Evidence actually exercises each failure mode the submitted scope claims to fix and shows an observable before/after or an equally decisive comparison with expected behavior. A documented deferral narrows which mode must be shown. A generic "tested locally", a suite pass without the target behavior, or a control/unchanged path alone fails. New tests must assert the changed behavior when tests are part of the plan. | required |
| repository-checks | Candidate PR test evidence and description compared with relevant test/build commands and explicit requirements in Repo facts and Plan context. | The relevant repository checks are run with identifiable outcomes, or any unavailable/failing check is explicitly reported with its reason and effect on readiness. A missing or failing check explicitly required for review holds; CI that can only run after the PR opens may be marked pending in a pre-submission draft, then must be checked on the opened PR. Do not require an irrelevant suite or invent a check absent from the package; targeted proof may suffice when no broader check is stated. | required |
| reviewable-diff | Entire Candidate PR unified diff and commit list compared with the issue's change boundary and plan. | A reviewer can isolate the fix and its supporting tests without debug output, commented-out experiments, dead code, broad formatting churn, or unrelated hunks. Judge actual diff content; weak commit titles alone do not fail a focused diff. | required |
| stated-standards | Repo facts' PR template, contribution requirements, AI-use policy, and relevant maintainer thread directions compared with Candidate PR title, description, and diff. | Applicable stated asks are substantively met: required template/checklist or issue-link content, required supporting files, and any AI-use disclosure with tool/extent when the repo requires it. Treat eval candidate work as AI-assisted when applying an explicit all-AI-use disclosure rule; silence under that rule fails. Do not invent a template, disclosure requirement, or policy where none is stated. Equivalent wording can satisfy a request without mirroring its heading. | required |
| reviewer-clarity | Candidate PR description and evidence links compared with its actual change. | A reviewer can locate the change, key evidence, and known limitation without guessing; concise text can pass. Extra polish is welcome but never rescues a required failure. | preferred |

## Verdict rule

Return `accept` only if every required check is `pass`. Return `reject` if any required check is `fail` or `unclear`; an unverifiable necessary fact cannot earn readiness. Preferred checks never change the verdict. Grade `fail` when evidence shows an unmet condition, `unclear` when necessary evidence is genuinely unavailable after checking the mapped location, and `pass` only with a deciding fact or quote. Run every check even after one fails. Apply explicit repository requirements as written, and never infer extra rules from personal preference.
